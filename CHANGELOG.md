# Changelog (newest first)

## 2026-11-12 (night, Dubai) - One store for the page: the skill posts outside readings to the app, and the page prefers the app database (v0.13.0)
- **Why:** the outside figures reached the page through the skill -> Home Assistant -> page chain, which dropped 107 of 426 hours and left the sensor stuck. Decision (James): record everything in the app's database and let the page read that; Home Assistant and the IQAir page are inputs, not what the page depends on.
- **New endpoint `POST /api/inbound/outside`** (secret in `X-Outside-Secret`, new env var `OUTSIDE_INGEST_SECRET`, 24+ characters; blank switches it off). Takes 1 to 1000 hourly rows `{page_time_dubai, temp_c, humidity_pct, us_aqi, pm25, wind_kmh}`, stores them in `outside_readings` (source `skill`). Unreadable or future times and rows with no plausible figure are skipped; out-of-range figures are dropped; a missing figure never wipes a stored one; posting an hour again is harmless, so the skill can post its whole file to fill the missing hours.
- **The page prefers the app database.** For every range the stored copy (tower history from the collector's Home Assistant sync, outside readings from the skill) wins for an hour it has; Home Assistant fills the hour in progress and anything not copied yet. Live tiles still read Home Assistant first (a stored hourly figure can be up to an hour old). The earlier rule (Home Assistant wins) is reversed.
- **Tower sensors to the app database:** already done by the collector's hourly sync (v0.11.1); unchanged.
- Docs: skill instructions in admin-guide (item 8); `OUTSIDE_INGEST_SECRET` in configuration, `.env.example` and both compose files (app container).
- Tests: 86 pass (3 new: ingest needs the secret, stores/skips/repeats safely and never wipes a figure, off when no secret; the Home Assistant-versus-copy test now expects the copy to win).
- **Untested:** the real skill posting to the live site (the skill's environment must allow an outbound HTTPS POST; not checked), PostgreSQL behaviour of the upsert on the live database. The IQAir collector fetch stays blocked (429) and on hold.

- **Charts:** a gap longer than 6 hours (3 days on All time) now breaks the line instead of drawing a straight run across it; short gaps are still bridged.
- **Known limit:** the skill writes whole degrees and whole percent (IQAir shows integers), so the outside line will still step. Smoother figures need a source with decimals (the IQAir API or Open-Meteo), not display tricks.
- **Outside collector status:** the collector's first live fetch of the IQAir page was refused (HTTP 429). The outside collector is on hold; the Claude scheduled skill stays as the outside source, and `OUTSIDE_POLL_MINUTES=720` slows the retries. The tower history copy works (9078 hourly figures, 16 sensors copied on first run). Options if revisited: IQAir API key or Open-Meteo.
- Tests: 84 pass (1 new for the stuck-run rule). **Untested:** the chart line breaks in a browser.

## 2026-11-12 (night) - The collector also keeps an hourly copy of the Home Assistant sensor history, and the page works from it when Home Assistant is offline (v0.11.1)
- **Why:** the tower readings (X-Sense and the others) were kept only in Home Assistant, so losing, replacing or restarting it meant losing the charts. Data is now recorded in one place and copied to the other: Home Assistant stays where readings are first recorded; the app's database holds a replica.
- **The `collector` container now has a second job.** When `HA_URL`, `HA_TOKEN` and `HA_AIR_SENSORS` are set on it, about once an hour (and on every cycle until it works) it reads Home Assistant's long-term statistics for every sensor the page charts (towers, extra sensors, and any `sensor.`/`source:name` outside ids) and upserts the hourly means into the new table `sensor_readings(sensor_id, hour_utc, value, fetched_at)` (migration `010_sensor_readings`; Fahrenheit stored as Celsius). The first run, and any sensor with no stored rows yet (for example one added to the layout later), copies everything Home Assistant holds; later runs re-read from three hours before the newest stored hour, which also heals any gap from the collector being down. `node api/dist/collector.js --sync-ha` runs it once by hand.
- **The page uses the copy.** For every range the charts take Home Assistant's figure for an hour it has and the stored copy for any hour it lacks. If Home Assistant cannot be reached, the page no longer gives up: the charts come entirely from the stored copy, the tiles show the last stored hour marked as an old reading, the unreachable notice shows, and no calls are made to Home Assistant (so the page is not slow while it is down). A live read that fails is now an empty reading rather than an error for the whole page.
- **Admin > System** shows "Tower history copy, newest hour"; the log has "Sensor history: working / Home Assistant unreachable" entries only when the state changes (the "Outside station" and "Sensor history" states are tracked separately; the filter button is now "Collector").
- Compose files: the `collector` service gets `HA_URL`, `HA_TOKEN` and `HA_AIR_SENSORS` (`docker-compose.unraid.yml`; a new `docker-compose.mres-with-collector.yml` for the Proxmox stack).
- Tests: 82 pass (5 new: copy with Fahrenheit and repeat safety, full-then-incremental start times, state logging, page fed from the copy with Home Assistant down, Home Assistant's figure winning over the copy). One existing privacy test now looks for an entity-id shape (`sensor.name`) instead of the text "sensor.", because the reference-band prose says "this sensor." and is now returned when Home Assistant is down.
- **Untested:** the sync against the real Home Assistant (statistics WebSocket with many sensors and the whole history in one call, which has a 90 s limit on the first run), the PostgreSQL migration `010_sensor_readings`, and the container on the Proxmox VM. History older than 72 hours is not used for tile fallback (a tile shows blank if Home Assistant has been down longer than that for a sensor with no recent stored hour); the charts still show everything stored.

## 2026-11-12 (evening) - Outside station collector: its own container keeps the outdoor readings in the app's database (v0.11.0)
- **Why:** the outside line depended on a scheduled Claude task that read the station page and wrote into Home Assistant through MetaMCP. When that chain broke, the `sensor.iqair_palm_*_log` sensors sat on one value (29.0 °C / 68 % since midnight on 12 Nov, while the station moved between 27 and 29 °C) and the outside tiles would have gone stale. The fetch now lives inside the stack.
- **New container `collector`** (same image as the app, command `node api/dist/collector.js`, added to `docker-compose.unraid.yml`; a snippet for the Proxmox `docker-compose.mres.yml` is in docs/unraid.md). Every `OUTSIDE_POLL_MINUTES` (default 20, minimum 10) it fetches `OUTSIDE_SOURCE_URL` (default the Palm Jumeirah station page on iqair.com), reads the station's own figures and the time the page gives for them, and stores one row per hour in the new table `outside_readings` (migration `009_outside_readings`: hour, temperature, humidity, US AQI, PM2.5, wind, page time, source, fetched time). It never runs migrations itself (it waits for the app to create the table), so the two containers cannot race.
- **Rules it keeps:** a figure is stored only with the page's own time (a page that stopped updating is never stamped with the time of the fetch); nothing is estimated or carried forward; values outside a plausible range are dropped; a later report for the same hour fills in missing figures and never wipes stored ones; repeat fetches make no duplicates. Parsing tries JSON embedded in the page first (taking the newest report up to now, so forecasts and history are ignored), then the visible "Last updated ... Temperature ... Humidity" text.
- **First start** with an empty table loads the 426 hours of earlier station readings kept in `api/seed-data/outside-readings.csv` (25 Oct to 12 Nov 15:00 Dubai, copied into the image). `node api/dist/collector.js --import-csv FILE` adds more; existing hours are never overwritten.
- **The Fresh air monitoring page** reads these rows when `HA_AIR_SENSORS` uses `"outside":{"temperature":"app:outside_temperature","humidity":"app:outside_humidity"}` (new id kind, no Home Assistant involved for the outside line). Tiles show the latest stored hour (labelled hourly, old after three hours, like the imported series); Day/Week/Month use hourly rows, All time uses daily averages by Dubai day. The old `sensor.` and `iqair:` ids still work.
- **Admin > System** shows the newest stored outside report, and the log gains an "Outside station" entry only when the state changes (working, page not updating, fetch failing). A failing fetch also records a short description of what the page contained so a changed layout can be fixed from the log.
- **Fix found on the way:** the Home Assistant statistics WebSocket helper could re-enter its own error handler when a connection failed while still connecting (closing the socket fired the error again, ending in a stack overflow). It now finishes once and detaches its handlers first. Both statistics readers.
- Tests: 77 pass (21 new in `api/test/outside.test.ts`: JSON and text parsing, forecast and history ignored, zone-less time refused, implausible values dropped, merge and idempotence, CSV import, cycle state logging, the page reading `app:` ids across all four ranges). Typecheck and build pass; the collector was run against a temporary SQLite database (seed import and a failed fetch logged).
- **Untested:** the parser against the real iqair.com page (the workspace cannot reach the site, so the page layout was assumed from earlier fetches; run `node api/dist/collector.js --check` in the container to see exactly what it reads), the migration on PostgreSQL, the collector container on the Proxmox VM, and the container health check. IQAir's site terms may not allow automated fetching: check before relying on it (see docs/security.md). Hours between 12 Nov 15:00 and the first live fetch are missing.

## 2026-10-15 - v0.4.0: photos are checked and faces covered on the phone before upload; scorecard additions

## 2026-10-09 - Photo upload fix
- Cause (most likely): Docker creates the bind-mounted `files` folder as root while the app runs as user `node`, so saving a photo failed with a permission error (HTTP 500) and the report form could not continue.
- Fix: new `docker-entrypoint.sh` starts as root, `chown`s the photo folder, then drops to `node` (via `setpriv`). No manual `chown` needed any more.
- The Dockerfile now sets the entrypoint's executable bit and strips CRLF itself (uploading via the GitHub website drops the +x flag, which stopped the container starting).
- The web client now shows a clear message when the server/proxy returns a non-JSON error (e.g. 413 too large) instead of failing silently.
